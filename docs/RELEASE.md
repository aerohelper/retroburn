# Build and release engineering

| | |
|---|---|
| Status | Packaging and release workflows built in the release milestone (M11); first release not yet tagged |

## 1. Continuous integration (`.github/workflows/ci.yml`)

Runs on every push to `main` and every pull request.

| Job | Runner | Steps |
|---|---|---|
| Build and test | `ubuntu-latest`, `windows-latest` | Temurin JDK 25 → `mvnw -B verify` (compile, unit and architecture tests, formatting and SPDX headers, credits completeness, coverage) |
| Licence and repository checks | `ubuntu-latest` | `reuse lint`; fail if a private planning document is in the tree |

Linux installs `xorriso cdrskin genisoimage ffmpeg dvdauthor cdrdao` and
Windows installs FFmpeg (Chocolatey) before `verify`, so the integration
tests run with real tools; test media are generated by the tests.

Two more workflows:

| Workflow | When | What |
|---|---|---|
| `windows-tools.yml` | Pull requests touching `windows-tools/`; called by `release.yml` | Builds cdrdao (CD-Text spike), dvdauthor/spumux and FFmpeg from pinned source in MSYS2, checks each against what RetroBurn asks of it, and bundles the shipped tools with licences and corresponding source |
| `release.yml` | Pull requests touching `packaging/` or the tool scripts (dry run); pushed `v*` tags | Builds the `.deb`, `.msi`, portable `.zip` and SBOM; on tags only, creates the GitHub Release |

## 2. Packaging per OS

Both packages are built on their own OS's runner by `packaging/package.sh`
([LLD-packaging.md](design/LLD-packaging.md)). `jlink` builds a runtime with
the JDK modules RetroBurn needs; JavaFX's jars sit next to the app and are
on the launcher's module path ([ADR-0019](adr/0019-packaging-layout-and-bundled-tools.md),
refining [ADR-0010](adr/0010-classpath-application-on-jlinked-javafx-runtime.md));
`jpackage` makes the app image and the package.

| | Linux | Windows |
|---|---|---|
| Format | `.deb` (`.rpm` later) | `.msi` + portable `.zip` (app image) |
| Tool | `jpackage --type deb` | `jpackage --type msi` with WiX 5 (installed in the workflow with `dotnet tool install wix`) |
| External tools | `--linux-package-deps "xorriso, cdrskin, genisoimage, ffmpeg, dvdauthor"` | FFmpeg, ffprobe, dvdauthor, spumux and their DLLs in `tools\` of the install folder |
| Extras | Desktop entry, original icon, `legal/` | Start-menu entry, original icon, `legal/`, `tools\licenses\` |

Every package must contain the JDK and JavaFX `legal/` files; this is checked
in the built `.deb` and `.msi` before each release.

## 3. Windows code signing

Unsigned installers trigger SmartScreen warnings. A free code-signing
programme for open-source projects will be evaluated and recorded as an ADR.
Until then the README explains the warning.

## 4. Bundled-binary compliance checklist (every Windows release)

- [ ] Each bundled binary and DLL listed in `THIRD_PARTY_NOTICES.md`,
      `components.json` and the SBOM, with version and licence.
- [ ] Licence texts and notices of every bundled binary and its DLL
      dependencies shipped in the installer.
- [ ] Exact corresponding source (tarballs, patches, build scripts and
      configuration) attached to the GitHub Release.
- [ ] FFmpeg's configure line recorded; `--enable-nonfree` not used; licence
      stated accordingly (LGPL or GPL).
- [ ] Binaries built by `windows-tools.yml` from pinned versions and checksums,
      or a recorded exception (ADR) with pinned version, checksum and archived
      source.
- [ ] About screen and `THIRD_PARTY_NOTICES.md` point to the source location.

## 5. Release steps

1. Update `CHANGELOG.md`: move "Unreleased" entries under the new version.
2. Set the version in `pom.xml` (drop `-SNAPSHOT`), commit with sign-off.
3. Merge to `main`, then the owner tags `vX.Y.Z` on `main` and pushes the
   tag. Nobody else creates release tags.
4. `release.yml` builds `.deb`, `.msi`, `.zip`, `SHA256SUMS`, a CycloneDX
   SBOM (`retroburn-<v>.cdx.json`: Maven dependencies from the CycloneDX Maven
   plugin plus the bundled tools from `tools/manifest.tsv`) and
   `windows-tools-sources-<v>.zip`, and attaches them to a GitHub Release
   whose notes are the changelog section of that version.
5. Install each package on a clean machine and run the smoke tests from the
   manual checklist.
6. Bump to the next `-SNAPSHOT` version.
